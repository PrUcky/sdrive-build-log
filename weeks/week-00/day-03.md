# Day 03 — Keys and Secrets

**Week:** 00 · **Date:** 2026-08-21 · **Hours:** ~4.5

Today was focused entirely on foundational security hygiene. Before I flash a Linux kernel or expose a single network socket to my local LAN next week, I wanted the administrative cryptographic layer and the repository guardrails to be rock solid. In embedded systems and home server administration, bad security habits established during day one prototypes have a nasty tendency of surviving all the way into production.

## What I actually did

I started by generating the dedicated administrative SSH keypair that will control root access to the Radxa ROCK 3C. I opened my terminal and executed:

```bash
ssh-keygen -t ed25519 -a 100 -C "sdrive-admin@radxa-prototype"
```

The `-a 100` flag instructs `ssh-keygen` to perform 100 Key Derivation Function (KDF) rounds using bcrypt to encrypt the private key on disk, dramatically increasing the computational cost required to brute-force the local passphrase if someone ever gains physical access to my laptop. The utility generated the keypair along with the distinctive ASCII art visualization, writing the private key to `~/.ssh/id_ed25519` and the public counterpart to `~/.ssh/id_ed25519.pub`.

I took some time to write down the exact mathematical and operational rationale for choosing `Ed25519` over traditional `RSA-4096` or `ECDSA` (such as NIST P-256):
- **Performance on Low-Power ARM CPUs:** Ed25519 operations rely on elliptic curve point addition over the twisted Edwards curve $-x^2 + y^2 = 1 - \frac{121665}{121666} x^2 y^2$ over the prime field $\mathbb{F}_{2^{255}-19}$. Signature generation and verification are blazingly fast and require minimal CPU cycles compared to massive modular exponentiations required by 4096-bit RSA keys.
- **Side-Channel Attack Immunity:** Ed25519 algorithms are specifically designed to execute in constant time. They do not use secret-dependent memory lookup tables or secret-dependent branching, which completely eliminates cache-timing and execution-timing side-channel attacks.
- **Compact Key Signatures:** An Ed25519 public key is exactly 32 bytes long (256 bits), and signatures are only 64 bytes. This makes key management, network payloads, and configuration files clean and lightweight compared to the sprawling 500+ character strings generated by RSA-4096.

This research naturally reinforced why password authentication must be completely disabled in the SSH daemon configuration (`PasswordAuthentication no`) the moment the board boots. If you expose an SSH server to any network, automated botnets will immediately begin hammering port 22 with dictionary attacks, cycling through thousands of common passwords per hour. A standard human password rarely exceeds 40 to 50 bits of practical entropy. In contrast, an Ed25519 private key provides a full 128-bit security level against quantum-classical search algorithms and 256 bits of raw entropy. Brute-forcing an Ed25519 private key would require more energy than is consumed by our entire solar system over its lifespan.

Next, I turned my attention back to the repository's secret scanning infrastructure. I authored the formal `.gitleaks.toml` configuration file in the root of the project. I wanted rules that would catch high-entropy strings without generating dozens of false positives every time I committed a standard base64-encoded SVG or hash string.

I configured custom regex rules specifically targeting sensitive assignment patterns, such as:
- Generic API tokens: `(?i)(?:api_key|secret|token|password|auth_token)\s*[:=]\s*['"][a-zA-Z0-9_\-]{16,64}['"]`
- Private key headers: `-----BEGIN (?:RSA|OPENSSH|EC|PGP) PRIVATE KEY-----`
- Cloud credential signatures for AWS, Tailscale auth keys (`tskey-auth-[a-zA-Z0-9]+`), and MinIO/Garage access tokens.

To verify that the engine actually halts dirty commits, I created a canary test file named `canary_test.env` containing a simulated token (`TAILSCALE_AUTH_KEY="tskey-auth-k9876543210abcdef123456789"`) and attempted to stage and commit it. The Gitleaks pre-commit hook immediately intercepted the Git pipeline, printed a red violation banner with the exact file path and line number, and aborted the commit before any ref was generated. I deleted the canary file, ran a clean scan, and verified that the repository history remained pristine.

I spent the final hour of the day reading through the Armbian documentation for Rockchip RK3566 target images. I learned that Armbian supports two distinct kernel tracks: the legacy vendor BSP kernel (Linux 5.10.x, which includes Rockchip’s proprietary multimedia blobs) and the mainline Linux kernel (Linux 6.6+ LTS). Because our architecture deliberately eschews server-side GPU/NPU video transcoding in favor of zero-knowledge blob storage, we can run the clean mainline LTS kernel without needing vendor BSP hacks.

## What confused me

I had a brief moment of second-guessing myself when reviewing asymmetric cryptography key placement. Even experienced developers occasionally make the mental slip of confusing which key lives where. I drew a small diagram in my notes to lock it in forever: the **Public Key** (`.pub`) is the padlock that you distribute freely and copy into the server's `~/.ssh/authorized_keys` file; the **Private Key** is the physical key that remains strictly on your local development workstation with file permissions set to `chmod 600`. The private key must never, under any circumstances, be copied onto the server, transmitted over the wire, or committed to source control.

The second area of friction was tuning the entropy thresholds in `.gitleaks.toml`. When I first applied a Shannon entropy check of 4.5 across all staged files, Gitleaks started flagging standard SHA-256 commit hashes and UUIDs in documentation as potential credential leaks. I refined the configuration to restrict entropy calculations strictly to variable assignments and configuration blocks while skipping markdown body text.
