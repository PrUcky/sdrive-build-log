# Day 15: DNS Lies, Firewall Walls, and the Routing Table That Decides Everything

*September 5, 2026*

I woke up this morning with a question that had been nagging at me since yesterday's `tcpdump` session: we proved that raw TCP works, but what happens before TCP? What happens in those invisible milliseconds between typing a hostname and the kernel actually knowing where to send packets? The answer is DNS. And DNS, as today proved, is the single most lied-to layer in the entire networking stack.

I SSH'd into the ROCK 3C and started from first principles. Where does this board think it should resolve names?

```bash
root@sdrive:~# cat /etc/resolv.conf
# Generated by NetworkManager
nameserver 192.168.1.1
```

One line. One nameserver. The home router. This is what every consumer device on our subnet sees — the ISP's recursive resolver, proxied through the router's built-in stub. It works, until it doesn't. I wanted to understand what "works" actually means at the wire level before I start trusting it with production traffic.

I installed `dnsutils` to get `dig`, the only DNS diagnostic tool worth using. `nslookup` is deprecated and hides critical information. `dig` shows you the raw DNS wire format, including authority records, TTLs, and the flags that tell you whether you're getting a cached answer or a fresh recursive lookup.

```bash
root@sdrive:~# apt install -y dnsutils
root@sdrive:~# dig ente.io

; <<>> DiG 9.18.28-1~deb12u1-Debian <<>> ente.io
;; global options: +cmd
;; Got answer:
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 41823
;; flags: qr rd ra; QUERY: 1, ANSWER: 2, AUTHORITY: 0, ADDITIONAL: 1

;; ANSWER SECTION:
ente.io.                300     IN      A       76.76.21.21
ente.io.                300     IN      A       76.76.21.22

;; Query time: 14 msec
;; SERVER: 192.168.1.1#53(192.168.1.1) (UDP)
;; WHEN: Fri Sep 05 10:22:41 IST 2026
;; MSG SIZE  rcvd: 68
```

14 milliseconds. Two A records. The `ra` flag confirms our router is doing recursive resolution on our behalf. The 300-second TTL means this answer will be cached for five minutes before the router bothers to ask upstream again. Fine for a desktop browsing experience. Completely unacceptable for a production appliance that needs to resolve S3-compatible storage endpoints reliably.

Here's the problem: if that router reboots, or if the ISP's recursive resolver has a bad day, or if some upstream CDN rotates IPs faster than the TTL, our appliance goes blind. The storage daemon can't find its own bucket endpoint. Uploads stall. The user sees a spinner and assumes their photos are gone.

I wanted to see what happens when DNS lies to us. I didn't have to simulate it — I just had to force the board to query a server that would give wrong answers. I pointed `dig` at a public resolver with an intentionally wrong query to see the failure mode:

```bash
root@sdrive:~# dig @192.168.1.1 thisdomaindoesnotexist.invalid

;; ->>HEADER<<- opcode: QUERY, status: NXDOMAIN, id: 52019
;; flags: qr rd ra; QUERY: 1, ANSWER: 0, AUTHORITY: 1, ADDITIONAL: 1

;; AUTHORITY SECTION:
.                       3600    IN      SOA     a.root-servers.net. nstld.verisign-gti.com. ...
```

`NXDOMAIN`. Clean, honest failure. The root servers told us the domain doesn't exist and the resolver faithfully passed that along. But ISP resolvers don't always play fair. Some intercept NXDOMAIN responses and redirect them to advertising pages. Some inject their own A records for parked domains. Some cache aggressively and serve stale data for hours after an upstream record change.

This is why production infrastructure never relies on a single resolver. I added Cloudflare's `1.1.1.1` and Google's `8.8.8.8` as fallback nameservers, then tested resolution through each independently to establish a latency baseline:

```bash
root@sdrive:~# dig @1.1.1.1 ente.io +stats | grep "Query time"
;; Query time: 8 msec

root@sdrive:~# dig @8.8.8.8 ente.io +stats | grep "Query time"
;; Query time: 12 msec

root@sdrive:~# dig @192.168.1.1 ente.io +stats | grep "Query time"
;; Query time: 14 msec
```

Cloudflare wins. Eight milliseconds from the edge of our ISP's CGNAT to Cloudflare's anycast PoP. That's faster than the local router because the router has to recursively query upstream anyway, adding a hop. For our appliance, the optimal configuration is: try Cloudflare first, fall back to Google, and use the router as a last resort.

I hardened the resolver configuration by writing a `systemd-resolved` drop-in:

```bash
root@sdrive:~# mkdir -p /etc/systemd/resolved.conf.d
root@sdrive:~# cat > /etc/systemd/resolved.conf.d/01-sdrive-dns.conf << 'EOF'
[Resolve]
DNS=1.1.1.1 8.8.8.8 192.168.1.1
FallbackDNS=1.0.0.1 8.8.4.4
DNSSEC=allow-downgrade
DNSOverTLS=opportunistic
Cache=yes
CacheFromLocalhost=no
EOF

root@sdrive:~# systemctl restart systemd-resolved
root@sdrive:~# resolvectl status
Global
       Protocols: +LLMNR +mDNS +DNSOverTLS DNSSEC=allow-downgrade
resolv.conf mode: stub
         DNS Servers: 1.1.1.1 8.8.8.8 192.168.1.1
Fallback DNS Servers: 1.0.0.1 8.8.4.4
```

DNS-over-TLS set to opportunistic means the resolver will encrypt queries when the upstream server supports it, but won't break if it doesn't. DNSSEC is set to `allow-downgrade` because our ISP almost certainly doesn't pass DNSSEC signatures cleanly, and hard-failing on validation errors would lock us out of the internet. Paranoia has to be balanced against availability.

With DNS bulletproofed, I turned to the firewall. The ROCK 3C has been running with UFW in a permissive state since Week 01's bootstrap script. Today, we lock it down properly.

```bash
root@sdrive:~# ufw status verbose
Status: active
Logging: on (low)
Default: deny (incoming), allow (outgoing), deny (routed)

To                         Action      From
--                         ------      ----
22/tcp                     ALLOW IN    192.168.1.0/24
```

Good baseline. SSH is allowed only from our local subnet, everything else is denied by default. But we're about to start serving HTTP endpoints, running S3-compatible storage on port 3900, and exposing PostgreSQL on 5432. Each of those services needs precisely scoped firewall rules. I added them now, before the services exist, so that when Week 03's containers come up, the firewall is already waiting for them:

```bash
root@sdrive:~# ufw allow from 192.168.1.0/24 to any port 8080 proto tcp comment 'museum API (Week 03)'
root@sdrive:~# ufw allow from 192.168.1.0/24 to any port 3900 proto tcp comment 'garage S3 (Week 03)'
root@sdrive:~# ufw allow from 127.0.0.1 to any port 5432 proto tcp comment 'postgresql localhost only'
root@sdrive:~# ufw status numbered
     [1] 22/tcp                     ALLOW IN    192.168.1.0/24            # SSH admin
     [2] 8080/tcp                   ALLOW IN    192.168.1.0/24            # museum API (Week 03)
     [3] 3900/tcp                   ALLOW IN    192.168.1.0/24            # garage S3 (Week 03)
     [4] 5432/tcp                   ALLOW IN    127.0.0.1                 # postgresql localhost only
```

Notice: PostgreSQL is bound exclusively to `127.0.0.1`. Not the LAN subnet. Not the Tailscale overlay. Localhost only. The database has no business accepting connections from any network interface. The `museum` Go backend connects to Postgres over the loopback adapter, and that is the only path. This is the principle of least privilege applied at the network layer.

Then came the part I was dreading. I needed to understand the routing table. Not the simplified version you see in blog posts. The real one. The actual kernel data structure that decides, for every single outbound packet, which interface to send it through and which next-hop MAC address to ARP for.

```bash
root@sdrive:~# ip route show
default via 192.168.1.1 dev eth0 proto dhcp src 192.168.1.150 metric 100
192.168.1.0/24 dev eth0 proto kernel scope link src 192.168.1.150 metric 100
```

Two entries. That's it. The entire routing decision tree for this machine fits in two lines. The first line says: "for anything not on our local subnet, send it to `192.168.1.1` via the `eth0` interface." The second line says: "for anything on `192.168.1.0/24`, deliver it directly on `eth0` without going through a gateway."

When Tailscale comes online, it will inject a third entry — a `100.64.0.0/10` route pointing through the `tailscale0` virtual interface. That's how the WireGuard overlay coexists with the physical LAN: the kernel looks at the destination IP, checks it against the routing table top-to-bottom, and the first matching prefix wins. Tailscale-addressed traffic goes through the encrypted tunnel. LAN traffic goes straight to the wire. The kernel doesn't care that one of those interfaces is a virtual userspace construct and the other is a physical Realtek PHY. To the routing table, they're both just numbered entries.

I deliberately broke the default route to see what happens:

```bash
root@sdrive:~# ip route del default
root@sdrive:~# ping -c 1 1.1.1.1
connect: Network is unreachable
root@sdrive:~# ping -c 1 192.168.1.1
PING 192.168.1.1 (192.168.1.1) 56(84) bytes of data.
64 bytes from 192.168.1.1: icmp_seq=1 ttl=64 time=0.891 ms
```

LAN still works because the `/24` kernel route is still there. But the internet is gone. No default gateway means the kernel has nowhere to send packets destined for addresses outside our subnet. It doesn't fail silently — it fails immediately with `Network is unreachable`, which is actually the ideal failure mode. A clean, instant error is infinitely better than a mysterious timeout.

I restored the route before my SSH session could expire:

```bash
root@sdrive:~# ip route add default via 192.168.1.1 dev eth0
root@sdrive:~# ping -c 1 1.1.1.1
64 bytes from 1.1.1.1: icmp_seq=1 ttl=57 time=8.12 ms
```

Back online in under a second.

The last experiment of the day was the most sobering. I wanted to see what a DNS poisoning attack looks like from the victim's perspective. I temporarily pointed the board's resolver at a local `dnsmasq` instance I spun up on my desktop, configured to return `192.168.1.100` (my desktop's IP) for every query:

```bash
root@sdrive:~# dig @192.168.1.100 ente.io +short
192.168.1.100
```

There it is. The board now believes that Ente's production API server lives at my desktop. If the `museum` backend were running, it would happily try to push encrypted photo metadata to my Windows machine instead of the real upstream. The authentication would fail, of course, but the connection attempt itself reveals the board's identity and network position to whoever controls the poisoned resolver.

This is why DNS-over-TLS matters. This is why DNSSEC matters. This is why you never, ever trust a single resolver operated by someone else. And this is why our `systemd-resolved` configuration uses opportunistic TLS encryption and maintains three independent resolvers from three different organizations.

I tore down the poisoned resolver, flushed the board's DNS cache with `resolvectl flush-caches`, and verified clean resolution was restored. The board is back to its hardened state.

Today the network stopped being an abstraction. DNS is not "it just works" — it's a fragile chain of trust that can be intercepted, poisoned, cached stale, or simply go offline. The firewall is not "a thing you turn on" — it's a whitelist of precisely scoped rules that must be written before the services they protect. And the routing table is not "something the DHCP server handles" — it's the single most important data structure on the machine, and deleting one line from it severs the board from the entire internet.
